# Conversational Quality Benchmark Design

**Date:** 2026-08-10

**Status:** Approved for implementation planning

**Scope:** Measurement only. This design does not change Anthon's prompt, turn planner, model routing, or production behavior.

## Objective

Create a repeatable way to determine whether changes to Anthon make it more conversational and better grounded in the user without hiding regressions in safety, usefulness, concision, latency, or cost.

The benchmark keeps `openai/gpt-5.6-luna` fixed. It compares the current behavior with a candidate behavior offline, using the same synthetic scenarios and an evaluator that does not know which answer came from which version.

User feedback remains external to the application: the product owner will report tester feedback manually. This project does not add an in-product survey, analytics event, feature flag, or production A/B allocation.

## Evidence from Tester Conversations

A read-only audit covered the complete available 30-day history of the agreed Production tester cohort:

- 8 active testers out of 10;
- 25 chats and 411 messages;
- 203 assistant responses, 202 generated by `openai/gpt-5.6-luna`;
- 23 multi-turn chats;
- 56.2% of responses started with a formula such as an acknowledgment or generic confirmation;
- 40.9% contained a Markdown list;
- 52.2% ended with a question;
- 10.3% combined acknowledgment, list, and question in the same response;
- at least 15 certain instances of premature advice appeared across 9 chats;
- about 29 of 106 final questions had low information value;
- at least 10 certain context or continuity failures appeared across 4 chats;
- multi-turn progression was good in 13 chats, mixed in 7, and weak in 3.

The audit did not modify Production and no tester transcript or personal data will be copied into benchmark fixtures. The findings inform synthetic scenario archetypes only.

## Existing Foundation

The implementation must extend the canonical Reality Benchmark rather than introduce a parallel evaluation system. The existing foundation already provides:

- database-backed synthetic users, chats, profiles, preferences, and memories;
- multi-turn execution through the real `streamChat` path;
- explicit model overrides that do not change production routing;
- deterministic heuristic scoring;
- two independent LLM judges with calibrated low and high anchors;
- JSON and Markdown artifacts under `docs/benchmarks/runs/`;
- explicit approval before database-mutating runs.

The existing dimensions remain intact. Conversational quality is added as a separate diagnostic layer.

## Conversational Quality Dimensions

Each eligible turn receives five scores from 0 to 10. Every score includes a short rationale and structured diagnostic labels.

### Discovery Before Advice

Measures whether Anthon recognizes when missing information could materially change its advice.

High scores require Anthon to ask before prescribing when context is insufficient and to proceed without unnecessary questions when context is already sufficient. Premature plans, routines, diagnoses, or conclusions reduce the score.

### Question Quality

Measures whether a question has information value for the next coaching decision.

A high-value question is specific, relevant, answerable, not already resolved by available context, and likely to change the next response. Ritual confirmation, generic continuation prompts, forced choices after a complete solution, stacked questions, and repeated questions reduce the score.

### Context Use

Measures correct use of the current transcript, profile, preferences, and available memories.

High scores require using relevant known information and avoiding questions whose answers are already available. Forced or irrelevant personalization, identity confusion, and unsupported recall reduce the score.

### Conversational Naturalness

Measures whether the response feels like part of a coherent dialogue rather than a fixed template.

The evaluator considers structural repetition, formulaic acknowledgment, unnecessary lists, generic motivational language, and ritual final questions. A list, acknowledgment, or final question is not inherently negative; it is penalized only when it is poorly matched to the turn.

### Multi-turn Progression

Measures whether later turns incorporate new information, deepen understanding, and move toward a more specific intervention.

Repeating variants of the same routine, ignoring corrections, losing identity, or restarting discovery without cause reduces the score.

## Guardrail Dimensions

The existing safety, memory/context, concision, coaching usefulness, mobile/voice suitability, hallucination resistance, and follow-up judgment metrics remain visible. Latency and cost remain operational metrics.

No single blended score may hide these dimensions. In particular:

- any safety regression requires manual review and normally blocks promotion;
- a concision or latency regression above 5% is highlighted, not automatically rejected;
- every regression is reviewed in its scenario context;
- increased verbosity does not count as improved conversational quality by itself.

## Scenario Dataset

The canonical Reality Benchmark receives a tagged conversational subset based on anonymized archetypes from tester feedback:

1. a training request where age or current level is decision-critical;
2. a food-planning request where dietary constraints and schedule are missing;
3. a home-training request without known equipment or availability;
4. an ambiguous input that must be clarified before interpretation;
5. a complete answer followed by a ritual confirmation question;
6. a fact already stated earlier in the same thread;
7. an explicit identity correction that must persist through later turns;
8. a request for continuity across chats where the system must be transparent about available context;
9. repeated discussion of the same fear where the intervention must progress rather than restate a routine;
10. a positive reference conversation that specializes gradually as useful details emerge.

Scenarios use curated, synthetic Italian fixtures. They must not reproduce tester names, messages, emails, identifying circumstances, or full transcripts.

Tags include `discovery`, `question-quality`, `context-continuity`, `naturalness`, and `multi-turn-progression`. Each turn defines calibrated low and high anchors plus a scenario-specific rubric.

## Offline A/B Workflow

The benchmark compares a frozen baseline artifact with a candidate run. It does not split production traffic.

### Create Baseline

Before changing behavior:

```bash
bun run benchmark:conversation baseline \
  --label before-conversational-change \
  --samples 3
```

The baseline records:

- Git commit;
- model ID;
- benchmark and scenario schema versions;
- relevant non-secret configuration fingerprints;
- scenario and replica identifiers;
- assistant outputs and existing runtime metrics;
- generation timestamps.

The artifact is immutable input for later comparison.

### Run Candidate

After changing behavior:

```bash
bun run benchmark:conversation candidate \
  --baseline docs/benchmarks/runs/<baseline>.json \
  --samples 3
```

The command validates compatibility before execution. It refuses to compare artifacts when the scenario set, scoring contract, fixed candidate model, sample count, or relevant execution contract has drifted. The operator must then deliberately regenerate the baseline.

### Compare Blindly

```bash
bun run benchmark:conversation compare \
  --baseline docs/benchmarks/runs/<baseline>.json \
  --candidate docs/benchmarks/runs/<candidate>.json \
  --judge
```

For each matching scenario and replica, the comparator:

1. assigns baseline and candidate to `A` and `B` using a deterministic hidden ordering;
2. withholds variant, commit, and candidate model identity from the judges;
3. asks two independent judges for absolute conversational dimension scores;
4. asks for one pairwise verdict: `A`, `B`, `tie`, or `both_insufficient`;
5. records concise strengths, weaknesses, and reasons;
6. reveals variant identity only while aggregating the final report;
7. flags material judge disagreement for manual review.

The deterministic ordering derives from benchmark version, scenario ID, turn index, and replica ID. Regenerating a report from the same artifacts must not reshuffle A and B.

## Artifacts and Access

The benchmark is a repository CLI tool. It is not exposed in the production admin interface.

Outputs live under `docs/benchmarks/runs/`:

```text
conversation-<date>-baseline.json
conversation-<date>-candidate.json
conversation-<date>-comparison.json
conversation-<date>-comparison.md
```

The Markdown report is the primary review surface. The JSON report is the machine-readable source of truth.

The report contains:

- candidate wins, baseline wins, ties, and both-insufficient outcomes;
- deltas for each conversational and guardrail dimension;
- structural diagnostics for formulaic openings, lists, questions, and their combination;
- premature-advice and question-quality diagnostics;
- context-use and multi-turn progression failures;
- safety, concision, latency, and cost regressions;
- judge disagreement;
- full synthetic baseline and candidate outputs for manual review;
- scenario-level verdicts and aggregate summaries.

A future admin page may display already-generated reports read-only, but launching runs from the application is outside this scope.

## Decision Policy

The benchmark informs a case-by-case product decision. It does not promote changes automatically.

A change is a credible candidate for tester validation when:

- it introduces no unresolved safety regression;
- it reduces premature advice and low-value questions;
- it improves context use or multi-turn progression;
- it wins a meaningful share of blind comparisons;
- its improvement is not explained only by greater length;
- remaining regressions are few, localized, and understandable.

The report classifies outcomes as clear improvements, clear regressions, trade-offs requiring review, or inconclusive results. Human feedback reported by the product owner is mapped back to the same five conversational dimensions and considered alongside benchmark evidence.

## Runtime and Data Safety

- The CLI must never run against Production implicitly.
- Database-backed runs require the existing explicit mutation approval.
- Development or an ephemeral Neon branch is the intended target.
- Benchmark records use isolated synthetic users and are cleaned up after the run unless explicitly retained.
- Secrets, production prompts, tester transcripts, and personal identifiers must not appear in artifacts.
- Model calls and judge calls are explicit and report their measured cost.
- A run failure preserves enough non-sensitive metadata to diagnose the failure without presenting partial results as a valid comparison.

## Testing Strategy

Deterministic unit tests cover:

- conversational score schemas and validation;
- pairwise verdict validation;
- deterministic blind ordering;
- compatibility and drift rejection;
- replica pairing;
- aggregation of wins, losses, ties, and both-insufficient outcomes;
- structural diagnostics;
- scenario and dimension summaries;
- Markdown and JSON report generation;
- judge disagreement flags;
- rejection of incomplete or invalid runs.

Integration-level tests use fake executors and judges to verify the baseline, candidate, and compare workflow without network or paid calls. Existing Reality Benchmark tests continue to guard the canonical runner.

Live verification consists of one deliberately authorized smoke run on the development or ephemeral database, followed by a complete fixed-model baseline before any conversational behavior is changed.

## Out of Scope

- changing the system prompt or turn planner;
- changing the production model or fallback routing;
- production traffic allocation or feature-flag A/B testing;
- in-product feedback collection;
- copying or automatically judging tester conversations;
- an admin control for launching paid benchmark runs;
- automatic deployment or promotion based on benchmark scores.

## Implementation Boundary

Measurement must land and produce a reviewed baseline before work begins on prompt or planner behavior. The subsequent behavior change uses the frozen baseline as its comparison target.
