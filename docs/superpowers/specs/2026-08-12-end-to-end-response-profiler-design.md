# End-to-End Response Profiler Design

**Date:** 2026-08-12
**Status:** Approved design; pending implementation plan

## Goal

Give each completed Anthon response a trustworthy technical profile that explains both backend execution and user-perceived latency.

The profiler must:

- distinguish the first token generated by the provider from the first text received and visibly rendered by the browser;
- attribute model, provider, profile, attempts, tokens, and cost to the execution that actually ran;
- show sequential and parallel backend work without presenting overlapping durations as an additive waterfall;
- persist privacy-safe traces in every environment;
- expose detailed traces only through the existing owner- and role-aware technical-metrics boundary;
- remain best effort so profiling failures never turn a valid chat response into an error.

## Decisions

- Persist two separate versioned traces: `serverTrace` and `clientTrace`.
- Add both traces as nullable JSON fields on `MessageMetrics`.
- Collect and persist them in development, preview, and production.
- Keep the server and browser clock domains separate. Do not fabricate a shared absolute timeline.
- Store only relative durations and closed technical attributes. Never store prompts, response text, tool arguments, tool results, URLs, IP addresses, user-agent strings, or arbitrary labels in these traces.
- Keep existing scalar metrics and `executionRoute` for compatibility. New detailed latency views prefer validated trace data when present.
- Do not backfill historical messages. They remain valid legacy records with nullable trace fields.

## Current state

Anthon currently persists model, provider, token counts, cost, aggregate generation time, optional reasoning values, aggregate tool timing, RAG usage, and a bounded execution-routing trace. Memory recall details live in assistant metadata. Additional route, database, RAG, and prompt timings are emitted through the latency logger but are not correlated durably with a response.

The main limitations are:

- `generationTimeMs` starts at orchestrator entry and ends after model completion, so it includes preparation, recall, RAG, prompt construction, tool work, and generation rather than model generation alone;
- `routingOverheadMs`, recall timings, tool timings, and generation timings can overlap and are not safely additive;
- the provider TTFT is not the first visible text latency;
- tool timing is aggregate rather than per invocation;
- route setup and persistence timings are logs only;
- `reasoningTimeMs` is normally unavailable;
- the browser does not persist stream receipt, DOM insertion, visible-frame, or perceived completion milestones.

## Scope

The first release covers authenticated private Web chat responses. The backend trace infrastructure may be passed through the shared channel flow, but Telegram and WhatsApp have no browser trace and do not receive a new user-facing profiler in this release.

Server profiling covers:

- Web request setup and authentication;
- user, chat, quota, and inbound-message database work;
- attachment preparation and transcription when applicable;
- turn classification and routing preparation;
- conversation history, user context, durable fact recall, conversation recall, and RAG;
- prompt construction;
- each provider attempt and time to first generated token;
- individual tool executions;
- model streaming and completion;
- assistant-message persistence.

Client profiling covers:

- request initiation;
- stream opening and the first received chunk;
- the first non-empty text delta;
- the first assistant text inserted into the DOM;
- the first animation frame in which that text can be visible;
- stream completion;
- reconciliation with the persisted assistant message.

## Non-goals

- Distributed tracing across OpenRouter or an upstream provider's internal systems.
- Claiming that the residual between server TTFT and browser visibility is purely network latency.
- Capturing raw provider metadata in the new trace.
- Capturing content, reasoning text, tool payloads, or retrieved document text.
- Creating assistant messages solely to store traces for requests that fail before a response exists.
- Backfilling guessed values for historical messages.
- Replacing PostHog, structured logs, or the encrypted 30-day `AiTurnTrace` system.
- Adding a general observability dashboard in the first release.

## Architecture

### Request-scoped server collector

Create a request-scoped `ServerTraceCollector`. It uses a monotonic clock and has no global mutable state. The Web route creates it at handler entry and passes it through the channel-flow and orchestrator options.

The collector provides small operations with clear ownership:

- `startSpan(name, attributes?)` returns an idempotent completion handle;
- `measure(name, operation, attributes?)` records an asynchronous span;
- `markFirstToken(attempt)` records the first non-empty generated token once;
- `snapshot(status)` validates and returns an immutable trace;
- bounded helpers record provider attempts and tool invocations using closed attributes.

Concurrent operations naturally produce overlapping spans because each span records `startOffsetMs` and `durationMs`. Parent identifiers may group related work, but rendering and analysis must not assume that child durations sum to the parent.

The collector must cap span count and trace size. Once the cap is reached it stops accepting new spans, marks the trace `partial`, and preserves already collected data.

### Server collector lifecycle

```text
Web route receives request
        |
        v
Create request-scoped collector
        |
        +-- route, DB, attachment, and quota spans
        |
        v
Pass collector into channel flow and orchestrator
        |
        +-- planning, context, RAG, recall, provider, tool, stream spans
        |
        v
Snapshot partial trace before assistant persistence
        |
        v
Persist Message + MessageMetrics + partial serverTrace atomically
        |
        v
Complete assistant_persistence span and totalMs
        |
        v
Best-effort MessageMetrics update with completed serverTrace
```

`serverTrace.totalMs` ends when the primary assistant-persistence transaction completes. The subsequent update that stores the finalized trace is deliberately excluded because a write cannot include its own completion time without recursion.

If finalization fails, the initial `partial` snapshot remains attached to the response. A profiler failure is logged but never propagated into chat delivery.

### Browser collector

Create one in-memory `ClientTraceCollector` per submitted user message, keyed by its existing browser-generated `clientMessageId`. The collector uses `performance.now()` and records each milestone at most once.

Transport instrumentation records request and stream receipt milestones. Chat state records the first non-empty text delta and stream completion. The assistant message surface reports the first non-empty DOM text and schedules `requestAnimationFrame` to record the first frame in which it can be visible.

The collector remains separate from React presentation state. Components emit milestones through a narrow callback and do not know how traces are persisted.

After the normal persisted-message refresh resolves the assistant response associated with the source `clientMessageId`, the browser submits the trace with a credentialed `keepalive` request. A small bounded retry handles the case where stream completion precedes durable-message visibility.

### Client-trace endpoint and correlation

Add an authenticated endpoint dedicated to the client trace:

```text
PUT /api/chat/messages/client-trace
```

The request contains:

```ts
{
  chatId: string;
  clientMessageId: string;
  trace: ClientTraceV1;
}
```

The server resolves the authenticated internal user, verifies private-chat ownership, resolves the inbound Web message by the owner-scoped `clientMessageId`, follows `generatedResponse`, and updates that assistant message's `MessageMetrics` row.

The browser never selects an arbitrary assistant-message row. If persistence has not completed, the endpoint returns a closed retryable error. If a valid client trace already exists, an identical retry succeeds without changing it; a different payload cannot overwrite it.

## Data model

The Prisma migration is additive:

```prisma
model MessageMetrics {
  // Existing fields remain unchanged.
  serverTrace Json?
  clientTrace Json?
}
```

There is no backfill. The fields inherit message lifecycle and deletion behavior through the existing one-to-one relation and cascade.

The first release does not add scalar summary columns. Existing fields remain available for established queries, while detailed traces remain versioned JSON. Privacy-safe scalar summaries may also be emitted to PostHog for aggregate analysis.

### Server trace contract

```ts
type TraceStatus = "completed" | "partial" | "cancelled";

type ServerSpanStatus = "completed" | "failed" | "cancelled";

type ServerSpanOutcome =
  | "completed"
  | "failed_before_stream"
  | "failed_during_stream"
  | "empty_response"
  | "not_allowed"
  | "cancelled";

type ServerSpanName =
  | "auth"
  | "user_lookup"
  | "chat_lookup"
  | "billing_sync"
  | "rate_limit"
  | "inbound_claim"
  | "attachment_resolution"
  | "transcription"
  | "classification"
  | "routing"
  | "history"
  | "user_context"
  | "memory_facts"
  | "conversation_recall"
  | "rag_decision"
  | "rag_embedding"
  | "rag_search"
  | "prompt_build"
  | "provider_wait"
  | "model_stream"
  | "tool"
  | "assistant_persistence";

type ServerTraceSpanV1 = {
  id: number;
  parentId?: number;
  name: ServerSpanName;
  startOffsetMs: number;
  durationMs: number;
  status: ServerSpanStatus;
  attributes?: {
    attemptSequence?: 1 | 2;
    profile?: "light" | "standard";
    model?: string;
    provider?: string;
    toolName?: string;
    ragChunkCount?: number;
    outcome?: ServerSpanOutcome;
  };
};

type ServerTraceV1 = {
  version: 1;
  status: TraceStatus;
  totalMs: number;
  timeToFirstTokenMs?: number;
  spans: ServerTraceSpanV1[];
};
```

Model, provider, and tool names are server-controlled strings capped at 128 characters. They are never copied from user content or provider error messages. A trace permits at most 96 spans, each offset and duration is capped at 15 minutes, and the complete serialized JSON is capped at 32 KiB. Reaching a collection cap produces a valid `partial` trace; an oversized client payload is rejected.

`timeToFirstTokenMs` means request receipt to the first non-empty generated text token. Per-attempt TTFT remains available on the existing `executionRoute`. The detailed profiler prefers `serverTrace` for end-to-end server timing and `executionRoute` for routing policy and attempt semantics.

### Client trace contract

```ts
type ClientTraceV1 = {
  version: 1;
  status: "completed" | "partial" | "abandoned";
  milestones: {
    requestStartedMs: 0;
    streamOpenedMs?: number;
    firstChunkReceivedMs?: number;
    firstTextDeltaReceivedMs?: number;
    firstDomTextMs?: number;
    firstVisibleFrameMs?: number;
    streamCompletedMs?: number;
    persistedMessageResolvedMs?: number;
  };
};
```

All values are finite, non-negative integer milliseconds relative to browser request start and capped at 15 minutes. Causally related milestones must preserve their partial order:

- request start <= stream open <= first chunk <= first text delta <= stream completion;
- first text delta <= first DOM text <= first visible frame;
- stream completion <= persisted-message resolution.

The visible frame may legitimately occur after stream completion when browser rendering is delayed, so the schema must not enforce a false total ordering across the network and rendering chains. A `completed` trace requires every milestone; missing milestones require a non-completed status.

When the document is hidden before a visible-frame measurement, the trace remains `partial`; the profiler does not claim that hidden content was visibly painted.

## Privacy and access control

Both schemas are strict allowlists. Unknown keys, arbitrary metadata, excessive arrays, excessive strings, invalid ordering, non-finite numbers, negative values, and oversized payloads are rejected.

The new traces never contain:

- user or assistant text;
- prompts or reasoning content;
- memory facts or conversation evidence;
- RAG queries, chunk text, document titles, or document URLs;
- tool arguments or results;
- provider error bodies or raw provider metadata;
- IP addresses, user-agent strings, browser fingerprints, or wall-clock timestamps.

Collection and persistence are enabled in every environment. Detailed delivery through chat APIs remains governed by the existing technical-metrics visibility policy: authenticated owner, private chat, and the current development/preference/role rules. Guests and public/shared viewers do not receive the traces.

The endpoint accepts only an owner-correlated trace and never returns another user's data. Existing technical response builders parse traces again before exposing them; malformed persisted JSON is omitted rather than forwarded.

## Profiler presentation

The technical panel begins with a compact summary:

- actual model, provider, and executed profile;
- server TTFT;
- first browser delta;
- first visible text;
- perceived completion;
- output throughput derived from output tokens and the applicable model-stream interval;
- token counts and cost;
- trace quality: `Complete`, `Partial`, or `Legacy`.

### Backend timeline

Render a waterfall normalized to server request receipt. Each row shows start position, duration, percentage of total server time, and status. Parallel work overlaps on the horizontal axis. The panel explicitly states that overlapping percentages are not additive.

Classification, context, recall, RAG, provider attempts, and tools are grouped. Expandable rows expose only validated technical attributes. The longest span may be highlighted as the dominant measured span, not asserted to be the exclusive root cause.

### Browser timeline

Render the browser milestones as separate network, rendering, and persistence lanes normalized to request initiation:

```text
Network:     Send -> stream open -> first chunk -> first delta -> stream complete
Rendering:                                      -> DOM -> visible frame
Persistence:                                                       -> resolved
```

Rows use the actual offsets. They do not assume that a visible frame always precedes stream completion.

The interface labels these distinct concepts:

- server TTFT: first non-empty token produced after the server receives the request;
- first delta: first non-empty text received by the browser;
- first visible text: first animation frame after non-empty assistant text reaches the DOM;
- perceived latency: request initiation to first visible text;
- perceived total: request initiation to stream completion.

The server and browser traces are not drawn on one supposedly shared clock. The difference between server TTFT and browser first-visible time may be shown as `outside measured backend`, which includes outbound request transit, response transit, SDK scheduling, throttling, React work, and paint opportunity. It must not be labeled simply as network latency.

### Responsive and legacy behavior

Desktop uses the full waterfall. Narrow screens use compact rows with text values and proportional bars without mandatory horizontal scrolling. Color is never the only status signal, controls remain keyboard accessible, and all visual measurements have text equivalents.

Historical responses without traces retain the existing technical summary and display `Legacy data`. Partial traces show their available milestones and a clear incompleteness indicator rather than substituting zeroes.

## Failure handling

- Collector methods never throw into chat execution.
- Span handles are idempotent so cancellation and error cleanup cannot double-complete a span.
- Reaching a span or size cap marks the trace partial and stops additional collection.
- Invalid persisted trace data is omitted at read time and logged with bounded identifiers.
- The initial partial server snapshot is written in the assistant transaction; failure of the final update leaves that snapshot intact.
- Client-trace submission is asynchronous and does not extend the chat loading state.
- A retryable pending-target result uses bounded backoff. Authorization and validation failures are not retried.
- A valid existing client trace is immutable.
- Requests that fail before an assistant message exists remain observable through structured logs and PostHog routing events; the system does not create synthetic assistant messages.

## Telemetry

Existing structured latency logs remain available during implementation and diagnosis. The request-scoped collector becomes the durable per-response source rather than the process-wide latency logger's transient entries.

The existing `$ai_generation` event may receive validated server summary scalars. Successful client-trace ingestion emits a separate privacy-safe event with first delta, first visible text, perceived completion, trace status, model, profile, and provider derived from the owned assistant row. No complete JSON trace or content is sent to PostHog.

## Performance budget

Profiling adds no external model or classifier calls. Runtime measurement uses monotonic local clocks and bounded in-memory arrays.

For a completed Web response the expected persistence overhead is:

- two nullable JSON fields on the existing metrics row;
- one best-effort update to finalize `serverTrace` after primary persistence;
- one asynchronous owner-scoped update to attach `clientTrace`.

Trace collection must remain bounded and must not delay first token delivery. Client submission starts only after normal response completion and does not block the next chat interaction.

## Migration and rollout

The Prisma migration adds only nullable fields and requires no data rewrite. Implementation validates the schema, runs Prisma generation, and applies the migration to the intended development target before integration verification. Production migration or deployment follows the repository's normal release workflow and is not implied merely by implementing the feature.

Because collection is required in every environment, there is no environment flag that disables the data contract. Failure isolation and nullable fields are the rollback mechanism. UI visibility remains independently controlled.

## Verification strategy

### Unit tests

- Strict parsing, bounds, monotonic milestone ordering, and version rejection.
- Trace redaction and rejection of content-like or arbitrary fields.
- Request-scoped collector behavior for sequential, parallel, failed, cancelled, duplicate-completion, and capped spans.
- Summary derivation and legacy fallbacks.
- First token, first delta, first DOM text, and first visible frame recorded exactly once.
- Hidden-document behavior produces a partial trace.

### Orchestrator and channel tests

- Standard and Light executions record the actual attempt, model, and provider.
- Pre-visible Light failure followed by Standard escalation records both attempts without relabeling the delivered model.
- RAG, durable facts, conversation recall, direct search, and multiple tool invocations produce bounded spans.
- Parallel context operations preserve overlapping offsets.
- Cancellation and provider failure close open spans safely.
- Assistant persistence writes a partial snapshot and finalizes it without changing response success semantics.

### API and persistence tests

- Prisma persistence round-trips both trace versions.
- Client-trace ingestion requires authentication and private ownership.
- Cross-user, public-chat, guest, malformed, oversized, and arbitrary assistant-target requests fail closed.
- Pending persistence returns only the defined retryable response.
- Identical retries are idempotent; conflicting overwrites are rejected.
- Invalid stored trace data is not exposed by chat or message APIs.

### Browser and runtime verification

- Send a real authenticated localhost chat response and confirm both traces against persisted `MessageMetrics`.
- Verify server TTFT, first received text, first visible text, and perceived completion remain distinct.
- Exercise a normal Standard response and, when available, Light, RAG/recall, and tool-bearing responses.
- Inspect desktop and compact mobile layouts for readability and overflow.
- Confirm the profiler remains hidden for guests and unauthorized/shared viewers.
- Confirm Next.js compilation and runtime error surfaces remain clean.

## Acceptance criteria

- Every newly completed authenticated private Web response attempts to persist a valid `serverTrace` in every environment.
- A completed visible Web response attempts to attach a valid `clientTrace` without blocking chat UX.
- The trace identifies actual execution and never infers a failed attempt as the delivered model or profile.
- Server TTFT, browser first delta, first visible frame, and perceived completion are separately named and measured.
- Parallel spans are represented with offsets and never presented as an additive decomposition.
- Trace payloads contain no user content, retrieved content, tool payloads, raw provider metadata, or fingerprinting data.
- Profiling, persistence-finalization, and client-ingestion failures do not fail or delay a valid chat response.
- Historical messages remain readable and are explicitly identified as legacy when detailed traces are absent.
- Detailed trace data is exposed only through the existing authorized technical-metrics boundary.
